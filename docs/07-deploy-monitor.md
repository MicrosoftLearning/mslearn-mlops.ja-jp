# Azure Machine Learning でモデルをデプロイおよび監視する

モデルのトレーニングは、機械学習ライフサイクルの始まりにすぎません。 価値を生み出すには、モデルを開発から運用環境に移行させ、その動作を監視し、データやパフォーマンスが変化したときに迅速に対応する反復可能な方法が必要です。

この演習では、以下のことを行います。

- GitHub Actions **環境**を使用して開発コンテキストでトレーニングを実行する。
- **共有 Azure Machine Learning レジストリ**にモデルを登録する。
- レジストリ モデルを**運用**環境のオンライン エンドポイントにデプロイする。
- ドリフトを監視し、開発環境で再トレーニングし、新しいモデル バージョンを運用環境に昇格させる
- 必要に応じて、以前のデプロイにロールバックし、不適切なモデル バージョンをアーカイブする

## 開始する前に

必要なもの:

- 管理レベルのアクセス権を持つ [Azure サブスクリプション](https://azure.microsoft.com/free?azure-portal=true)。
- リポジトリを作成し、GitHub Actions を構成するアクセス許可を持つ [GitHub](https://github.com/) アカウント。

## ワークスペースとデータ資産をプロビジョニングする

まず、開発と運用に必要な Azure Machine Learning ワークスペースとデータ資産を作成または再利用します。 前のラボで使用したのと同じパターンに基づいて構築します。元のラボ リポジトリからワークスペースとデータをプロビジョニングしてから、自動化用に別の GitHub リポジトリを接続します。

1. ブラウザーで Azure portal (`https://portal.azure.com/`) を開き、Microsoft アカウントを使用してサインインします。
1. ページの上部にある **[>_]** (**Cloud Shell**) ボタンを選択して Cloud Shell を開き、ダイアログが表示されたら **[Bash]** を選択します。
1. 正しいサブスクリプションと、**[ストレージ アカウントは不要]** が選択されていることを確認します。 次に、**[適用]** を選びます。
1. ターミナルで、このリポジトリをクローンし、インフラストラクチャ フォルダーに移動します。

    ```azurecli
    rm -r mslearn-mlops -f
    git clone https://github.com/MicrosoftLearning/mslearn-mlops.git mslearn-mlops
    cd mslearn-mlops/infra
    ```

1. セットアップ スクリプトを実行する前に、開発および運用フォルダーのデータ資産も個別に作成するように更新します。
    1. Cloud Shell で、エディターで `setup.sh` ファイルを開きます (たとえば、`code setup.sh` を実行します)。
    1. ファイルで、**データ資産の作成** セクションを見つけます。

        ```bash
        # Create data assets
        echo "Create training data asset:"
        az ml data create --type mltable --name "diabetes-training" --path ../data/diabetes-data
        az ml data create --type uri_file --name "diabetes-data" --path ../data/diabetes-data/diabetes.csv
        ```

    1. これらのコマンドの直後に、次の行を追加して、このリポジトリの開発および運用データ フォルダーを指すフォルダー データ資産を作成します。

        ```bash
        az ml data create --type uri_folder --name "diabetes-dev-folder" --path ../experimentation/data
        az ml data create --type uri_folder --name "diabetes-prod-folder" --path ../production/data
        ```

    1. ファイルを保存し、ターミナル ウィンドウに戻ります。

1. セットアップ スクリプトを実行します。

    ```azurecli
    ./setup.sh
    ```

    > 拡張機能がインストールできなかったというメッセージは無視してください。

1. スクリプトが完了するまで待ちます。 リソース グループ、Azure Machine Learning ワークスペース、コンピューティング リソース、およびこのラボに必要なデータ資産が作成されます。
1. Azure portal で、**[リソース グループ]** に移動し、作成された `rg-ai300-...` リソース グループを開きます。
1. Azure Machine Learning ワークスペース (`mlw-ai300-...` など) を選択し、**[スタジオの起動]** を選択して Azure Machine Learning スタジオを開きます。
1. スタジオで **[データ]** を選択し、次のデータ資産があることを確認します。
    - コア トレーニング データ用の `diabetes-training` という名前の **MLTable** またはファイル ベースの資産。
    - ワークスペース ファイル内の`experimentation/data` フォルダーを指す `diabetes-dev-folder` という名前の**ファイル (uri_folder)** データ資産。
    - `production/data` フォルダーを指す `diabetes-prod-folder` という名前の**ファイル (uri_folder)** データ資産です。

    これらのアセットのいずれかが見つからない場合は、表示されている型とパスを使用して手動で作成します。

このラボでは、開発データと運用データを表すために、1 つのワークスペースと個別のデータ資産を使用します。

## テンプレートから GitHub リポジトリを作成する

次に、GitHub Actions を使用できるように、元のラボ リポジトリから独自の GitHub リポジトリを作成します。 これは、前のラボで使用したのと同じテンプレート ベースのアプローチに沿っています。

1. ブラウザーで `https://github.com/MicrosoftLearning/mslearn-mlops` に移動します。
1. 右上隅の **[このテンプレートを使用する]** を選択し **[新しいリポジトリの作成]** を選択します。
1. **[所有者]** フィールドで、ご自分の GitHub アカウントを選択します。 **[リポジトリ名前]** フィールドに、`mslearn-mlops` などの名前を入力します。
1. **[Create repository from template](テンプレートからリポジトリを作成する)** を選択します。
1. テンプレートから作成した新しいリポジトリで、**[Actions]** タブに移動し、ダイアログが表示されたら GitHub Actions を有効にします。
1. 新しいリポジトリのクローン URL (`https://github.com/<your-alias>/mslearn-mlops.git` など) をメモします。 この URL は、リポジトリをローカルで、または開発環境から操作する場合に使用します。
 
テンプレートベースのリポジトリの準備ができ、ワークスペースが既にプロビジョニングされているので、GitHub を Azure に安全に接続できるようになりました。

## GitHub リポジトリ、環境、シークレットを準備する

次に、開発環境でトレーニングを実行し、後で運用環境からデプロイできるように GitHub を設定します。

1. ブラウザーで、`MicrosoftLearning/mslearn-mlops` テンプレートから作成したリポジトリに移動します。
1. リポジトリで、**[Actions]** タブに移動し、ダイアログが表示されたら GitHub Actions を有効にします。
1. リポジトリで、**[設定]** > **[環境]** に移動します。
1. 環境を 2 つ作成します。
    - `dev`
    - `prod`
1. Azure portal の Cloud Shell で、リソース グループに対して **[共同作成者]** アクセスがあるサービス プリンシパルを作成します。 次のコマンドを実行する前に、`<service-principal-name>`、`<subscription-id>`、`<your-resource-group-name>` を置き換えます。

    ```azurecli
    az ad sp create-for-rbac --name "<service-principal-name>" --role contributor \
        --scopes /subscriptions/<subscription-id>/resourceGroups/<your-resource-group-name> \
        --sdk-auth
    ```

1. 完全な JSON 出力をコピーし、一時的に保存します。 これを両方の環境でシークレットとして追加します。
1. GitHub リポジトリで、**[設定]** > **[環境]** に移動し、`dev` 環境を選択します。
1. `AZURE_CREDENTIALS` という名前の新しい環境シークレットを追加し、サービス プリンシパルからの JSON 出力を値として貼り付けます。 シークレットを保存します。
1. 両方の環境に `AZURE_CREDENTIALS` シークレットが含まれるように、`prod` 環境に対して前の 2 つの手順を繰り返します。
1. (省略可能) `prod` 環境で、この環境でジョブを実行する前に手動での承認が要な**環境保護ルール規則**を追加します。

GitHub は、環境固有のシークレットと保護ルールを使用して、開発と運用の両方について Azure に対して認証できるようになりました。

## pull request から開発でモデルをトレーニングして検証する

次に、テンプレートベースのリポジトリで GitHub Actions ワークフローを使用します。これにより、トレーニング構成に対して変更が提案されるたびに、開発データに対してモデルがトレーニングされます。

1. テンプレートから作成した `mslearn-mlops` リポジトリを、ファイルの編集や変更のプッシュができる開発マシンにクローンします。
1. ローカル クローンで、`src/train-model-parameters.py` を開き、次の動作が行われる方法を確認します。
    - ファイルまたはフォルダー パスからトレーニング データを読み取る。
    - ロジスティック回帰モデルをトレーニングし、**正確性**や **AUC** などのメトリックをログに記録する。
1. `src/job.yml` を開き、`training_data` 入力のプレースホルダー値を置き換えて、コマンド ジョブが既定で開発フォルダー データ資産を使用するようにします。

    ```yml
    inputs:
      training_data:
        type: uri_folder
        path: azureml:diabetes-dev-folder@latest
    ```
1. `src/job.yml` を開き、Azure Machine Learning コマンド ジョブで次の動作が行われる方法を確認します。
    - `aml-cluster` コンピューティングで `train-model-parameters.py` を実行する。
    - 既定で、`diabetes-dev-folder` データ資産を指す `training_data` 入力を使用する。
    - 構成可能な `reg_rate` ハイパーパラメーターを受け入れる。
1. `.github/workflows/train-dev.yml` のワークフローを確認して、次の動作が行われる方法を確認します。
    - `dev` 環境で `AZURE_CREDENTIALS` シークレットを使用して Azure にサインインする。
    - `infra/setup.sh` スクリプトで作成されたリソース グループとワークスペースを検出する。
    - `src/job.yml` で定義されている Azure Machine Learning ジョブを送信し、`diabetes-dev-folder` データ資産を使用するために `training_data` 入力をオーバーライドする。
    - ジョブのログをストリーミングし、出力から**正確性**と **AUC** 値を解析し、pull request にコメントとして投稿します。
1. ローカル クローンで、`.github/workflows/train-dev.yml` 開き、`pull_request` トリガーを追加して、pull request によってトレーニング コードが変更されたときにのみワークフローが自動的に実行されるようにします。

    ```yml
    on:
      workflow_dispatch:
      pull_request:
        branches:
          - main
        paths:
          - 'src/train-model-parameters.py'
          - 'src/job.yml'
    ```
1. ローカル クローンで、新しい機能ブランチを作成し、小さく安全なハイパーパラメーターの変更を加えます。 たとえば、`src/train-model-parameters.py` にある `--reg_rate` の既定値を調整します。
1. 変更をコミットして新しいブランチを GitHub にプッシュします。
1. GitHub で、機能ブランチから `main` への pull request を作成します。
1. [pull request] ページで、追加した `pull_request` トリガーにより、**開発環境のモデルのトレーニング**ワークフローが自動的に実行されることを確認して、完了するまで待ちます。
1. ワークフローの実行が完了したら、pull request のコメントを確認します。 トレーニング ジョブからの開発の**正確性**と **AUC** の値を含むワークフローからのコメントが表示されます。

開発ワークフローは既定では手動のままであり、トリガーを追加した後にのみ pull request に対して自動的に実行が開始されます。 これにより、準備ができたら pull request 検証を有効にしつつ、不要な実行がライブ リポジトリから除外されます。

## pull request コメントから運用データでモデルを再トレーニングする

開発トレーニングの結果が妥当と思われる場合は、GitHub Actions の運用データ資産と `prod` 環境を使用する運用トレーニングの実行を要求できます。

1. GitHub リポジトリで、**[設定]** > **[環境]** を開き、(先ほどの `dev` の場合と同様に) `AZURE_CREDENTIALS` シークレットが構成された `prod` 環境があることを確認します。
1. 開発の実行を検証したのと同じ pull request で、コマンド `/train-prod` を含む新しいコメントを独自の行に追加します。
1. **[Actions]** タブで、コメントへの応答として **運用環境のモデルのトレーニング (pull request コメント)** ワークフロー (`.github/workflows/train-prod.yml` で定義) が開始されていることを確認します。
1. ワークフローが完了するまで待ちます。 ワークフローは次のようになります。
    - `prod` 環境で `AZURE_CREDENTIALS` シークレットを使用して Azure にサインインする。
    - 開発に使用したのと同じ Azure Machine Learning ワークスペースを検出します。
    - `src/job.yml` コマンド ジョブをもう一度送信します。今回は、`diabetes-prod-folder` データ資産を使用するために `training_data` 入力をオーバーライドします。
    - ログをストリーミングし、出力から**正確性**と **AUC** を解析し、それらを別のコメントとして pull request に投稿します。
1. **運用**評価メトリックを含む pull request に関する新しいコメントを確認します。 これらの値を開発メトリックと比較して、運用環境に似たデータに対するモデルの動作を理解します。

コメント コマンドを使用して運用トレーニングをトリガーすると、pull request のディスカッションの一環として結果をキャプチャしながら、運用ワークロードの実行タイミングを制御できます。

## pull request コメントからリアルタイム エンドポイントにモデルをデプロイする

開発と運用のトレーニングが完了し、確認を終えたので、Python スクリプトとコメントでトリガーされる別のワークフローを使用して、マネージド オンライン エンドポイントにモデルをデプロイする準備が整いました。

1. ローカル クローンで、`src/deploy_to_online_endpoint.py` を開き、次の動作が行われる方法を確認します。
    - `DefaultAzureCredential` と `MLClient` を使用して、Azure Machine Learning ワークスペースに接続する。
    - オンライン エンドポイント (たとえば、`diabetes-endpoint`) が存在することを確認するか、必要に応じて作成する。
    - ローカルの `model` フォルダー内の MLflow モデルを使用するデプロイ (`blue` など) を作成または更新する。
    - エンドポイント トラフィックの 100% を指定されたデプロイに転送し、スコアリング URI を出力する。
1. `.github/workflows/deploy-prod.yml` のワークフローを確認して、次の動作が行われる方法を確認します。
    - pull request の `/deploy-prod` コメントをリッスンする。
    - `prod` 環境と `AZURE_CREDENTIALS` シークレットを使用して Azure に対する認証を行う。
    - `infra/setup.sh` で作成されたサブスクリプション、リソース グループ、ワークスペースを検出する。
    - 検出された値を使用して `deploy_to_online_endpoint.py` を実行し、MLflow モデルをマネージド オンライン エンドポイントにデプロイする。
1. pull request で、独自の行に `/deploy-prod` を含むコメントを追加します。
1. **[Actions]** タブで、**モデルをオンライン エンドポイントにデプロイする (pull request コメント)** ワークフローの実行を確認し、正常に完了するまで待ちます。
1. ワークフローが完了したら、デプロイを確認する pull request の新しいコメントを確認します。 次に、Azure Machine Learning スタジオで **[エンドポイント]** > **[リアルタイム エンドポイント]** に移動し、`diabetes-endpoint` を選択し、**[テスト]** タブを使用してサンプル要求を送信します。

運用のエンドポイントは、pull request ベースのワークフローを通じてトレーニングおよび確認されたモデルを提供するようになりました。開発環境と本番環境のメトリックが pull request に表示され、スクリプト化されたデプロイを繰り返して拡張できる状態です。

## データ収集を有効にしてモデルの監視を構成する

ドリフトと品質の問題を監視するには、Azure Machine Learning がエンドポイントから運用環境の推論データにアクセスする必要があります。

1. Azure Machine Learning スタジオのリアルタイム エンドポイントで、**[設定]** または **[データ収集]** セクションを開きます。
1. 入力と出力がワークスペース データストアに格納されるように、エンドポイントの **[モデル データ収集]** を有効にします。
1. 変更を保存します。
1. 左側のナビゲーションで、**[監視]** (または、ワークスペース ビューに応じて **[モデルの監視]**) に移動します。
1. 新しい監視を作成し、オンライン エンドポイントに関連付けます。
1. 次のような設定でモニターを構成します。
    - **監視シグナル**: **データ ドリフト**を有効にします。
    - **参照データ**: トレーニング データ資産 (`diabetes-dev-folder` など) を使用します。
    - **運用データ**: オンライン エンドポイントから収集されたデータを使用します。
    - **頻度**: 適切なスケジュール ("毎日" など) を設定します。
1. 監視を保存して有効にします。

最初の監視の実行が完了したら、ドリフト スコアなどのメトリックを確認し、運用データの分布がトレーニング データから乖離しているかどうかを確認できます。

## pull request ワークフローを使用してドリフトをシミュレートし、再トレーニングする

実際のシステムでは、ドリフトやパフォーマンスの低下によって再トレーニングがトリガーされます。 このラボでは、トレーニング パラメーターを変更し、前に使用したのと同じ pull request ベースの開発環境 → 運用環境 → デプロイのフローを繰り返すことで、これをシミュレートします。

1. 監視が少なくとも 1 回実行されるまで待ってから、Azure Machine Learning スタジオのドリフト メトリックを確認します。
1. リポジトリのローカル クローンで、再トレーニング作業を表す新しい機能ブランチを作成します。 次に例を示します。

        ```bash
        git checkout -b feature/drift-retrain
        ```

1. `src/train-model-parameters.py` を開き、既定の正則化率または別の安全なパラメーター (たとえば、`--reg_rate` の既定値を調整する) を変更して、ドリフトに対応する方法を設定します。
1. 変更をコミットしてブランチを GitHub にプッシュします。

        ```bash
        git add src/train-model-parameters.py
        git commit -m "Retrain in response to drift"
        git push --set-upstream origin feature/drift-retrain
        ```

1. GitHub で、`feature/drift-retrain` ブランチから `main` への新しい pull request を作成します。
1. 先ほど追加した `pull_request` トリガーにより、**開発環境のモデルのトレーニング** ワークフローが新しい pull request に対して自動的に実行されることを確認します。 完了したら、更新された **dev** の正確性と AUC を示すコメントを確認します。
1. 開発メトリックに問題がなければ、pull request にコメント `/train-prod` を追加して、**運用環境のモデルのトレーニング (pull request コメント)** ワークフローをトリガーします。 完了したら、更新された **prod** の正確性と AUC を示すコメントを確認します。
1. 運用のメトリックも問題なければ、pull request にコメント `/deploy-prod` を追加して、**オンライン エンドポイントにモデルをデプロイする (pull request コメント) ** ワークフローをトリガーします。 完了するまで待ちます。
1. 最後に、Azure Machine Learning スタジオで、**[エンドポイント]** > **[リアルタイム エンドポイント]** に移動し `diabetes-endpoint` を選択し、**[テスト]** タブを使用して、再トレーニングとデプロイ後もエンドポイントから予測が返されることを確認します。

シミュレートされた誤差に対応して、同じ pull request ベースの開発 → 運用 →デプロイのワークフローを繰り返すと、監視、再トレーニング、および制御された昇格がエンドツーエンドの MLOps プロセスでどのように連携するかを確認できます。

## (省略可能) 以前のモデル バージョンにロールバックする

新しくデプロイされたモデルで回帰が発生したり、運用環境で予期しない動作が発生したりする場合は、ワークフローを再実行することなく、直接 Azure Machine Learning スタジオで以前のバージョンにロールバックできます。

1. Azure Machine Learning スタジオで、**[エンドポイント]** > **[リアルタイム エンドポイント]** に移動し `diabetes-endpoint` を選択します。
1. **[デプロイ]** タブで、デプロイの一覧を確認します。 最近デプロイしたモデル バージョンに関連付けられている現在の `blue` デプロイが表示されます。
1. 以前のモデル バージョンからロールバック デプロイを作成するには、次の手順を行います。
    1. 左側のナビゲーションで **[モデル]** に移動し、モデルを開きます (`train`、または `model/MLmodel` ファイルで使用される名前など)。
    1. モデルの **[バージョン]** リストで、ロールバックするバージョン (たとえば、最新のデプロイの前のバージョン) を特定します。
    1. そのバージョンを選択し **[デプロイ]** > **[リアルタイム エンドポイント]** の順に選択します。
    1. デプロイ ウィザードで、**[既存のエンドポイント]** を選択して、`diabetes-endpoint` を選択します。
    1. 新しいデプロイに、`rollback` などの個別の名前を付けます。
    1. その他は既定値のままにして、**[デプロイ]** を選択します。
    1. デプロイが **[成功]** の状態になるまで待ちます。
1. `rollback` デプロイの準備ができたら、**[エンドポイント]** > **[リアルタイム エンドポイント]** > `diabetes-endpoint` に戻ります。
1. **[デプロイ]** タブで、**[トラフィックの更新]** を選択します。
1. `rollback` がトラフィックの **100%** になり、`blue` が **0%** になるようにトラフィック割り当てを設定します。 **[更新]** をクリックして変更を適用します。
1. **[テスト]** タブで、サンプル要求を送信して、エンドポイントがロールバック モデルのバージョンから予測を返すようになったことを確認します。
1. (省略可能) 問題のあるモデル バージョンにフラグを設定して今後のデプロイから除外するには、**[モデル]** に戻り、影響を受けるバージョンを開き、その **[ステージ]** を **[アーカイブ済み]** に設定します。

> **ヒント:** トラフィック ルーティングは直ちに更新されるため、UI でのロールバックはエンドポイントのダウンタイムなしで有効になります。 ロールバックが安定していることを確信したら、元の `blue` デプロイを **[デプロイ]** タブから削除して、ホスティング コストを削減できます。

## Azure リソースをクリーンアップする

Azure Machine Learning を調べ終わったら、不要な Azure のコストを避けるために作成したリソースを削除する必要があります。

1. [Azure Machine Learning スタジオ] タブを閉じて、Azure portal に戻ります。
1. Azure portal の **[ホーム]** ページで、**[リソース グループ]** を選択します。
1. Azure Machine Learning ワークスペースと関連するリソースを含む **[rg-ai300-...]** リソース グループを選択します。
1. リソース グループの **[概要]** ページの上部で、**[リソース グループの削除]** を選択します。
1. リソース グループ名を入力して、削除することを確認し、**[削除]** を選択します。
